## 核心问题

### 问题 1：功能原子被过度拆分

**案例：暂停恢复功能**
- 实际代码量：3 个文件，~150 行
- 真机验证：1 次（暂停成功 + 队列阻塞）
- 实际工作量：应该 2-3 小时

**但被拆成 5 个串行任务**：
```
T023 持久化可恢复检查点 [待联调] → 阻塞 29 个后续任务
  ↓
T024 发布/消耗/删除提交门禁 [待联调] → 阻塞 23 个后续任务
  ↓
T025 不确定外部结果核对 [待联调]
  ↓
T026 暂停请求与安全停止握手 [已完成] ← 今天做完这个
  ↓
T027 交还控制权并继续原任务 [进行中] ← 但前置未齐，无法继续
```

**问题**：
- 每个任务都要经历"8步骤 + 验收 + 接口契约 + 证据"流程
- 它们在代码里是**同一个文件的不同分支**
- 理解依赖关系的时间 > 写代码的时间

**类似的过度拆分**：
- 远程控制：8 个任务（T029-T036）
- 发布流程：5 个任务（T073-T077）
- 商品管理：5 个任务（T059-T063）
- 账号绑定：3 个任务（T007, T010, T011）
- 任务状态：3 个任务（T013, T014, T028）

**建议**：
- 暂停恢复合并为 1 个任务："暂停→恢复→继续"完整流程
- 远程控制合并为 2 个任务："WebRTC 会话 + 实时播放" + "手势控制面板"
- 每个合并任务一次真机验证覆盖 happy path + 主要错误分支

```
T117 Redmi 基线认证   深度=18 [未开始]
T076 选择帖子设备     深度=17 [未开始]
```

**平均每任务依赖 2.8 项**，但深度可达 20 层。

**问题**：
- 要完成 T120，必须先完成 20 层前置任务
- T027（恢复执行）依赖 T025, T025 依赖 T024, T024 依赖 T023
- 无法并行，只能串行等待

**实际情况**：
- T027 的 happy path（暂停→恢复→继续）**不需要等** T024 失败补偿、T025 结果核对
- 失败分支可以在 happy path 验证后再补充测试

**建议**：
- 区分"技术依赖"和"逻辑完整性依赖"
- 技术依赖：必须先有接口才能调用（比如 T029 WebRTC 会话 → T032 实时播放器）
- 逻辑完整性依赖：可以分批验证（比如 T027 恢复成功 + T025 恢复失败核对）
- **只标注技术依赖**，逻辑完整性通过分批测试覆盖

- 真机验证次数：**每个任务 1-2 次**
- 代码文件数：**3-8 个**

## 优化建议

### 方案 A：大幅合并（推荐）

**原则**：
- 按**功能闭环**合并，不按"需求逻辑完整性"拆分
- 每个任务一次真机验证覆盖主流程
- 失败分支单独补充测试

**合并示例**：
```
原 T023-T027 (5 个任务) → 新 T02X 暂停恢复 (1 个任务)
  验收：暂停→人工处理→恢复→继续发布

原 T029-T036 (8 个任务) → 新 T03X 远程控制 (2 个任务)
  T03A: WebRTC 会话 + 实时播放
  T03B: 手势控制 + 交还自动化

原 T073-T077 (5 个任务) → 新 T07X 发布流程 (2 个任务)
  T07A: 多图选择 + 填入 + 发布判断
  T07B: 任务工厂 + 字段映射
```

**预期效果**：
- 任务数：120 → 40-50
- 依赖深度：最大 20 → 最大 6
- 平均完成时间：半天/任务 → 1 天/任务
- 总工期：按现在进度需要 60 天 → 优化后 25-30 天

### 方案 B：调整依赖策略（保守）

**不合并任务，但区分依赖类型**：
- 技术依赖（MUST）：必须先完成
- 逻辑依赖（SHOULD）：建议完成，但可以用 mock
- 验收依赖（TEST）：主流程验证后补充测试

**示例**：
```
T027 交还控制权并继续原任务
  技术依赖 (MUST): T026 暂停握手
  验收依赖 (TEST): T025 结果核对, T011 换绑阻断
```

**执行策略**：
- 先做 MUST 依赖的任务
- 主流程验证通过后，标记"核心完成"
- 再补充 TEST 依赖的失败分支

**预期效果**：
- 任务数：120（不变）
- 但可以并行验证主流程
- 失败分支可以集中补充测试
